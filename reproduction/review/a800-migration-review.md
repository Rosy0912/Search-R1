## Verdict

**Current code cannot safely resume merely by changing the model directory.** A narrow, explicitly accepted **weight continuation** is feasible after the changes below. It is not a complete checkpoint restart: Adam moments, RNG state, sampler/epoch position, and optimizer/scheduler state were never saved. User acceptance of that limitation is a prerequisite to starting the continuation; migration preparation and source inspection can proceed independently.

The original pure-EM Search-R1 reward, GRPO groups, generated-token masks, retrieval corpus, original-base KL reference, 64-question intermediate validation and full terminal evaluation should remain unchanged. A machine change must not silently turn the run into an Instruct-model or shaped-reward baseline.

## Blocking semantics and minimal changes

1. **Keep actor and reference initialization separate.** `verl/workers/fsdp_workers.py:304` initializes actor from `self.config.model.path`, while line 335 initializes the reference from the same path. Directly substituting `global_step_K` therefore changes the KL target to the already trained model. Keep the existing model path fixed to the original verified Qwen2.5-3B base and add an explicit actor-only checkpoint path, used only in the actor/rollout initialization branch. `_build_rollout` at lines 268–279 consumes the actor module/config and FSDP synchronization, so verify that its initial generation also uses the continued actor. The driver tokenizer (`verl/trainer/main_ppo.py:145–149`) may remain the original base only after tokenizer identity has been verified. Require reference-path provenance in the run manifest; fail closed if it equals the continuation checkpoint.

2. **Call the operation weight continuation.** `fsdp_workers.py:509–527` saves HF model state and tokenizer only. Fresh AdamW is created at lines 229–240. There is no stored optimizer/RNG/sampler state to recover. Preserve that fact in the manifest and logs; do not claim numerical equivalence to an uninterrupted H20 run. Resume from the latest *complete, validated saved checkpoint*, not from the highest metric line: unsaved later updates are lost. Record the source completed update K, checkpoint hashes, original-base hashes, dataset/retriever versions and new segment start time.

3. **Restore logical count and schedule, without adding 500 new updates.** Trainer `fit` currently resets the counter to zero and starts at 1 (`ray_trainer.py:683–695`). Start at K+1; retain original terminal configuration 501 so the final actual update remains 500 (`:870–881`). Retain the original warmup denominator: `int(.285*501)=142` (`fsdp_workers.py:234–240`), not a new remaining-update denominator. The schedule is constant-after-warmup, not linear decay: `verl/utils/torch_functional.py:424–429` implements `min(1,current_step/142)`. The worker advances the scheduler *after* each actor update (`fsdp_workers.py:381–383`). Thus the next resumed update must use LR `1e-6*min(1,K/142)`, and the post-update logged LR for update K+1 is `1e-6*min(1,(K+1)/142)`. Initialize LambdaLR with the appropriate completed-step state and initial_lr, testing actual PyTorch initialization semantics to prevent its implicit initial step from creating an off-by-one. Do not fake K optimizer updates to advance the schedule. Fresh Adam moments remain fresh regardless of restored LR/count. Refuse invalid K, including K>=500; if K>495, five additional updates cannot fit inside the original budget and require an explicit decision.

4. **Five resumed updates need a new acceptance window and comparator.** Current `verify_five_updates.py:33–40` requires steps 1..5 and `global_step_5`, and its parameter comparison is against the original base near its final lines. For migration require this segment's actual updates K+1..K+5, save at K+5, and compare the saved q-projection against the validated *migration source checkpoint*. Comparing with the original base can falsely accept a job that only copied old H20 weights. Preserve all-tensor finite checks and canonical-schema checks against the original base. Preserve the strictly validated Qwen tied-head serialization exception; arbitrary missing keys or extras remain errors. Require fresh log/checkpoint timestamps for the A800 segment, hashes tying the source checkpoint to the transfer, and a new log/segment identity; do not combine prior-host metric lines with new-host metrics. The five-update checker stays read-only and must not terminate the same process that continues toward update 500.

5. **Do not import H20 preflight success as A800 readiness.** `reproduction/h20/run_training.sh:18–27` reuses ready markers and H20 environment/GPU result files. A new host needs its own real environment verification, eight-device visibility, BF16/NCCL, real Qwen/vLLM generation, GPU retrieval and HTTP retrieval validation. The launcher hardcodes `/data/search-r1`, GPU0..7, and vLLM utilization .6 (`train_paper_grpo.sh:4,13,48`); verify those paths and exclusive device availability on A800 rather than copying stale ready logs. Existing PID identity/pidfd cleanup must only manage the new segment's own retriever. Stopping/freeing H20 is the parent agent's separate authorized action; this review did not perform it.

## A800 memory and library qualification

- Eight 80-GB A800s have lower per-device capacity than the H20 target. The real FP32 flat index occupies roughly 64.56 GB; FP16 eight-way sharding is approximately 4.0 GB/device before FAISS scratch/resources and allocator overhead. E5 resides on one GPU as well. VLLM .6 can reserve a large portion of available device memory, while actor/reference initialization, FSDP gathering, generation and update add peaks. Index arithmetic alone does not establish safety. Measure actual free/device peaks with retriever already resident, then generation plus real updates. If necessary tune memory-only generation reservation or microbatch/accumulation while preserving global batch512, minibatch256, group size5 and objective; record every adaptation.
- Host RAM is not established by the local code. If the target has 128 GB, the ~64.56-GB CPU index, clone transients, Arrow/cache pages, Python/Ray processes, CPU optimizer offload and rank-0 checkpoint gathering require explicit headroom. `retrieval_server.py:210–217` loads/clones the index before the corpus; `gpu_retrieval_preflight.py:20–26` deliberately retains a CPU index alongside its GPU clone. Run preflight sequentially and fully exit it before starting the resident retriever/trainer. Observe available RAM, swap and clone peak instead of assuming the 128-GB host fits. Avoid simultaneously duplicating the real index in multiple processes.
- Keep FAISS GPU wheel in the isolated retriever overlay, not the training environment. Preserve async endpoint single-calling-thread semantics and real HTTP precheck; main-thread-only FAISS preflight did not validate HTTP by itself on H20. The H20 cuBLAS override and NVLS disable are project-local fixes, not proof they are required or sufficient on A800. Recreate pinned environment and run A800 checks without altering system CUDA/other users' installations.
- Transfer the verified saved checkpoint, original base, tokenizer, encoder, corpus/index and processed-data/config manifest. Verify content hashes at destination before use. Follow download memory: remote direct first, local relay only on stall/offline, preserve incomplete-target relay copies until all intended destinations verify. A checkpoint's semantic finite/schema test complements but does not replace transfer hashes.

## Required meaningful regression and runtime evidence

CPU tests should execute actual modified control flow/helpers rather than reimplement the formulas:

1. Actor-only continuation-path routing: actor and initial rollout receive saved weights while reference receives original base, with distinct sentinel paths/weights; reject a reference redirected to the continued checkpoint. Check tokenizer compatibility explicitly.
2. Counter control flow for K=5 and K=100: first logged update K+1; five gate/save at K+5; no stop at that gate; final save update500 and full seven-source final evaluation once. Include K=495 boundary, K=496 inability to supply five within budget, invalid K, and K=500 no accidental extra update. 64-question initial/intermediate evaluation remains bounded.
3. Real CPU AdamW/LambdaLR schedule comparison at K=0,1,5,141,142 and200: resumed first-used LR equals uninterrupted next-used LR, post-update logged LR has correct offset, 142 warmup remains unchanged. Also assert the new optimizer has no recovered Adam moments, accurately documenting weight-only semantics.
4. Gate rejection for old segment logs/stale shards, original-base-only parameter delta, copied unchanged source checkpoint, missing update in K+1..K+5, malformed source manifest, incomplete/mismatched/NaN weights and invalid tied-head duplicates. Valid reshards and exact valid Qwen tied duplicates still pass.
5. Read-only transfer/provenance tests: source K agrees with complete checkpoint and manifest, both source/destination hashes match, reference hashes remain original base, and the new segment cannot reuse H20 ready markers.

After CPU regressions and accepted weight-continuation semantics, parent-run A800 evidence must include host/device inventory, fresh environment/GPU/HTTP checks, successful 64-question initial validation, **five real resumed actor updates** with finite metrics and fresh complete checkpoint, source-to-new parameter change, and continued liveness of the same process. An hourly monitor should report meaningful failure/completion, distinguish unavailable from idle, and must not automatically restart duplicate trainers. These runtime criteria have not been executed by this reviewer.
