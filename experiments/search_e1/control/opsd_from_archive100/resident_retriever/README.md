No GPU is enumerated/initialized by `prepare_candidate.py`; `server.py` starts with CPU FP32 E5 and waits for process/source-bound activation.

`resident_scan.py` initially retains a single scanner and the **original global tile order**. It eliminates recurring full-index host→device transfers after resident loading. It does not combine shard-local top-k results or introduce a differently shaped final merge. Each request retains its query micro64 and tail, each tile retains its original full/tail GEMM shape, and each original local-top-k then running-top-k operator executes in order. At contiguous shard boundaries only query arrays and current FP32 score/int64 ID state are copied to the next device. There is no parallel per-shard arithmetic in this first candidate; a speed benefit is unmeasured until actual production timing is recorded.

CPU encoding remains original FP32 E5, independent per-request batch128/padding boundaries. The original configured Torch16/faiss32 directives are preserved, but actual thread counts are recorded. Existing scanner threads have reported Torch16/faiss144; configuration equality is not a claim of numeric equality. The complete320-query HTTP oracle comparison checks actual encodings and documents/order/scores together. CPU fixture evidence covers random/tied rankings, empty/query tails and shard/tile boundaries; it explicitly does not establish cross-GPU arithmetic or CUDA-copy equality.
